Coverage · Language support

Why blast radius is reliable for Go — and only Go

Three parsing technologies live in this repo, and the split is the whole story. It isn't a bug you can patch — it's a property of what each language's tooling can give you.

Blast radius needs two things at once

1

Function body line-ranges — to map a diff to functions. The mapper asks "which function's [start,end] contains these changed lines?" (diff_mapper.go:144). No accurate end line → the hunk overlaps nothing → the function is never flagged.

2

Cross-file call edges — to traverse. Reverse BFS walks "who calls this?" If resolution is name-guessing, the edges are wrong or missing and the traversal is noise.

Go gets both. TS/Python get neither reliably. That asymmetry is the answer.

The Go-only hybrid, precisely

Body ranges: here's the twist — scip-go doesn't even emit enclosing_range, so a SCIP occurrence is just the identifier token, one line. Go recovers real body bounds by re-parsing every file with go/ast (refineGoFunctionBounds, scip.go:257). That patch is Go-only.

Edges: both Go paths are strong — scip-go resolves via the real compiler, and even the fallback uses go/types for receiver types (golang.go:212). For JS/Python the fallback is tree-sitter — a parser, not a type checker — so it literally can't know store.Get() reaches PostgresStore.Get.

"Blast radius needs accurate function body ranges and accurate cross-file edges. Go is the only language with both — scip-go for identity, a go/ast re-parse for the body bounds SCIP omits, and a type-aware fallback. TS/Python get patchy SCIP coverage and a syntax-only fallback, so I marked them experimental rather than ship a review tool that quietly lies."

If asked "how would you fix the others?"

Lean on the SCIP indexers for TS/Python too (the path that makes Go reliable), validate coverage with the built-in validate-scip command, and gate non-Go output behind a confidence floor.
